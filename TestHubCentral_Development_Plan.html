1. Executive Summary

What we're building and why it matters.

Test Hub Central is a full-stack testing governance platform that lets Xmachina teams create compliance programs, manage test projects, browse test-suite catalogs, schedule automated test runs, view rich results, and automatically bridge failures into the existing Support Desk ticketing system.

Key Goals

  • Centralised governance: Programs → Projects → Scheduled Jobs → Results
  • Marketplace-style test-suite catalog with KPIs, scope, and certification metadata
  • Multi-framework test execution engine (Playwright + Cypress + Python) via Docker
  • Real-time results dashboard with pass/fail analytics and trend charts
  • Auto-ticket creation in Support Desk for every failed test case (zero manual logging)
  • Role-based team management (Admin, Tester, Viewer, External)
  • AI assistant for contextual dashboard queries

6. Support App Integration

Detailed design for the automatic ticket creation bridge.

6.1 — How the Support Desk API Works

The existing Support Desk exposes a single endpoint:

POST /api/query
Content-Type: application/json
Body: { "sql": "..." }
  • SELECT / WITH statements return { rows: [...] }
  • All other statements (INSERT, UPDATE) return { changes, lastInsertRowid }
  • The database uses SQLite with WAL mode (better-sqlite3)

6.2 — Integration Bridge Service

A dedicated Node.js module in the Testing Portal backend:

// services/integrationBridge.ts

interface TicketPayload {
  subject: string;        // "[FAIL] {testName} — {project} {env}"
  description: string;    // Error details, stack trace, screenshot URL
  priority: string;       // Mapped from suite severity
  category: 'bug';        // Always 'bug' for test failures
  customerName: string;   // 'TestHub-Automation'
  customerEmail: string;  // 'testhub@xmachina.digital'
}

async function createSupportTicket(payload: TicketPayload): Promise<number> {
  const sql = `INSERT INTO sd_tickets (subject, description, status, priority, 
    category, customer_name, customer_email) 
    VALUES ('${esc(payload.subject)}', '${esc(payload.description)}', 
    'open', '${payload.priority}', '${payload.category}', 
    '${esc(payload.customerName)}', '${esc(payload.customerEmail)}')`;

  const res = await fetch(`${SUPPORT_DESK_URL}/api/query`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ sql })
  });
  const data = await res.json();
  return data.lastInsertRowid;
}

async function addTicketMessage(ticketId: number, content: string) {
  const sql = `INSERT INTO sd_messages (ticket_id, sender_type, sender_name, content) 
    VALUES (${ticketId}, 'ai', 'TestHub-Bot', '${esc(content)}')`;
  
  await fetch(`${SUPPORT_DESK_URL}/api/query`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ sql })
  });
}

8. Development Phases

Six phases from foundation to production release.

Phase 1 — Foundation & Infrastructure

Weeks 1–3
  • Initialize monorepo structure: /client (React + MUI + Vite), /server (Node.js + Express), /runners (Docker)
  • Set up PostgreSQL schema with migrations (Prisma or Knex)
  • Set up Redis + BullMQ for job scheduling
  • Implement JWT authentication (Xmachina SSO integration)
  • Build global layout shell: collapsible sidebar, top bar (theme switcher, search, notifications, account menu)
  • Create MUI theme with dark/light mode support and design tokens from spec
  • Docker Compose for local development (app + postgres + redis + minio)
  • CI/CD pipeline skeleton (lint, type-check, unit tests)
  • Configure ESLint, Prettier, Husky pre-commit hooks
Deliverable: Running dev environment with authenticated shell, themed sidebar, and database.

Phase 2 — Core Modules (Programs, Projects, Test Suites)

Weeks 4–7
  • Dashboard: KPI cards, accordion sections, chart components (Recharts), live data queries
  • Programs: Create form, portfolio card grid, roadmap template selector, canvas viewer (React Flow)
  • Projects: 5-step creation wizard (MUI Stepper), project cards, edit/start/stop controls
  • Test Suites: Catalog grid with search/filter, detail drawer, "Add to Project" modal with program/app/env/schedule selection
  • Users: Team list, role assignment, invite flow, RBAC middleware on backend
  • Implement all CRUD REST APIs for each module
  • Seed database with catalog of test suite templates across all categories
Deliverable: All CRUD pages functional; users can create programs → projects → schedule jobs.

Phase 3 — Test Execution Engine

Weeks 8–10
  • Build Docker images for Playwright, Cypress, and Python test runners
  • Implement Test Orchestrator service: reads scheduled jobs, provisions containers via Docker API
  • Shared volume setup for results collection (JSON reports, screenshots, logs)
  • Results Aggregator: parse JUnit XML / JSON reports → normalize → store in test_results
  • WebSocket integration for real-time execution status updates to frontend
  • Job retry logic with configurable max attempts
  • BullMQ cron scheduling for recurring test jobs
  • Artifact storage in MinIO/S3 with pre-signed URLs for screenshot access
Deliverable: Tests execute in Docker containers on schedule; results stored and visible.

Phase 4 — Support Desk Integration Bridge

Weeks 11–12
  • Build Integration Bridge service (services/integrationBridge.ts)
  • Implement auto-ticket creation for failed test cases via POST /api/query to Support Desk
  • Implement auto-message attachment with error details, screenshots, and log links
  • Passed test case logging as instances in Support Portal
  • Build ticket_bridge_log table for full audit trail
  • Priority mapping engine (test severity → ticket priority)
  • Build Integrations settings page: connection config, toggle, health check, audit log viewer
  • Idempotency guard: prevent duplicate tickets for the same test failure in the same run
  • Error handling: queue failed bridge calls for retry
Deliverable: Failed tests auto-create tickets in Support Desk with full context. Audit trail visible.

Phase 5 — Results, AI Agent & Notifications

Weeks 13–15
  • Results module: Interactive charts, execution logs, historical trends, drill-down views
  • Status-based filtering (All / Passed / Failed / Skipped) with MUI DataGrid
  • Automated email reports to managers (Nodemailer + templates)
  • AI Agent: Python FastAPI service with LLM integration for contextual Q&A
  • Agent can answer: highest-used test cases, certification usage, active programs/projects count, failure patterns
  • Right-panel chat UI integrated into dashboard
  • Notification system: real-time alerts for test completions, failures, ticket creation
  • Global search implementation across all modules
Deliverable: Full results analytics, AI assistant, notification system, and email reporting.

Phase 6 — Testing, Polish & Production Release

Weeks 16–18
  • End-to-end testing of all user journeys with Playwright
  • Component testing of all MUI modules with Cypress
  • Integration testing of the Support Desk bridge (round-trip verification)
  • Performance testing and optimisation (bundle size, API response times, DB query tuning)
  • Security audit: input sanitisation (SQL injection prevention for bridge), RBAC verification
  • Accessibility audit (WCAG 2.1 AA compliance)
  • Production Docker images with multi-stage builds
  • Deployment configuration (Railway / Docker Swarm / K8s manifests)
  • Documentation: API docs (Swagger), user guide, runbook
  • Certification workflow: link resolved tests → program certification → release packaging
Deliverable: Production-ready, tested, documented platform with certification support.

Multi-layered approach using the same tools the platform orchestrates.

LayerToolScopeTarget Coverage

Component TestsCypress Component TestingAll MUI page components in isolation (forms, cards, wizards, data grids)All interactive components
API / Integration TestsCypress + SupertestREST API endpoints, auth flow, bridge calls to Support DeskAll endpoints
E2E TestsPlaywrightFull user journeys: login → program → project → execute → results → ticketAll critical paths
Visual RegressionPlaywright ScreenshotsKey pages across light/dark themesAll pages
PerformancePython (Locust / k6)API load testing, concurrent test execution stress testing100+ concurrent users
SecurityPython (OWASP ZAP)XSS, SQL injection (especially bridge queries), CSRF, auth bypassOWASP Top 10
Critical Security Note: The Support Desk API accepts raw SQL via POST /api/query. The Integration Bridge MUST use parameterized escaping (the existing esc() utility) and never pass unsanitised data from test outputs into SQL strings. Consider adding a dedicated REST endpoint on Support Desk for ticket creation as a Phase 2 enhancement.

11. Risks & Mitigations

Known challenges and how we'll handle them.

RiskImpactMitigation
SQL Injection via Bridge Critical Strict escaping via esc(); input validation; consider adding dedicated REST endpoints to Support Desk
Docker resource exhaustion High Container resource limits (CPU/memory); job queue concurrency cap; auto-cleanup of old containers
Support Desk unavailability High Retry queue with exponential backoff; health-check before batch; alert on consecutive failures
Large test result volumes Medium Pagination, result archiving after 90 days, DB indexing on status/date columns
Roadmap canvas complexity Medium Start with predefined templates only; custom builder as Phase 2 enhancement
AI Agent hallucinations Medium Ground responses with SQL queries to real data; show "based on" citations; human review toggle
